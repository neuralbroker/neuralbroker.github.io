Why I built neuDB

A small database project about transparency, persistence, and AI memory.

Most AI applications hide memory behind a managed database or a hosted vector service. That is convenient, but it can make the system difficult to inspect when something goes wrong. I built neuDB to understand the underlying pieces directly: how records are persisted, how writes remain safe after a failure, and how semantic retrieval fits into an ordinary data model.

neuDB stores each table as a human-readable JSON file. A record receives a UUID, and the core engine supports insertion, filtering, updating, deletion, and text search. Writes go through a temporary file, fsync, and atomic replacement. Per-file locks protect concurrent threads inside the process. The design is intentionally modest, but every decision is visible and easy to debug.

The bug the tests caught

When I added concurrency tests, my first design swept stray temp files on every table open — and the new test immediately broke it: the sweep deleted a live writer's temp file mid-write, failing its atomic rename. Cleanup-on-open is wrong under concurrency. Sweeping is now explicit maintenance with an age threshold, and the incident is documented in docs/recovery.md. That sequence — write the test, watch it catch a real race, fix the design — is the most valuable thing the project taught me.

What I measured

Benchmarks via benchmarks/bench.py: 138 inserts/s (p95 13.7ms) at 2,000 rows, falling to 56/s (p95 34.4ms) at 5,000 rows — O(N) writes confirmed, since every write rewrites the whole file. Threaded writers (4×100) lose nothing: 400/400 rows. The table is the deliverable: it says exactly where this design stops being viable (~10K rows per table), which makes the next design concrete instead of theoretical.

The AI layer adds optional embeddings to message records. Semantic search uses cosine similarity, while text search remains available when an embedding model is not installed. On top of that, the agent retrieves relevant messages before calling an LLM and stores the new exchange afterward. The result is a small long-term memory loop that can run locally with Ollama or connect to an OpenAI-compatible provider.

The project also clarified its limits. JSON files and linear scans are appropriate for a local tool, not a high-volume service. A production version would need indexes, transactions, process-safe coordination, pagination, and an approximate nearest-neighbour vector index. Those limitations are part of the value of the project: a simple implementation makes the next engineering problem concrete.

neuDB is available on GitHub and is published on PyPI, with the full case study at projects/neudb.
