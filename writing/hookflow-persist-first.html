HookFlow: accept first, deliver later

Webhook delivery is a persistence problem, not a POST problem.

The naive webhook sender does requests.post(customer_url, json=event) inside the request handler. That couples your API latency to the customer's worst day: their deploy, their timeout, their 500. I built HookFlow around the opposite order — persist the event and its delivery row first, acknowledge the producer, and let a worker own the unreliable part.

Constraints

One service, one database, one queue — no Kafka, no Kubernetes. Redis had to be optional: the system must stay correct on plain database polling, because an MVP that requires four daemons to be correct is an MVP that is never correct. Receivers must be able to verify every delivery and safely receive it twice.

Architecture

Client → FastAPI → PostgreSQL → Redis (hint) → Worker → webhook

The ingest path validates (http(s) URL, JSON-serializable payload under 256KB), checks idempotency, then commits Event + Delivery(status=queued) in one transaction before touching Redis. Redis only carries a wake-up hint; the worker polls due rows regardless, so a dropped message delays delivery instead of losing it. Measured on SQLite via TestClient: 39 rps at p95 29ms for 1KB payloads — the cost is the transaction, not the bytes.

The decision that mattered

At-least-once plus idempotency keys instead of exactly-once claims. A UNIQUE(endpoint_id, idempotency_key) constraint plus an IntegrityError catch closes the race where two concurrent ingests both pass the app-level existence check — the loser returns the winner as deduplicated. The application check is the friendly path; the constraint is the actual guarantee. The worker poll is indexed on (status, next_attempt_at) for the same reason: correctness mechanisms must not depend on tables staying small.

Failure and backoff

Backoff with a dead end: 1m → 5m → 30m → 2h → 12h across 5 attempts, then a dead-letter state with a replay endpoint that resets attempts. Successes are deliberately not requeueable — replaying one would duplicate a side effect at the receiver, and the API returns 409 to say so. Each delivery is HMAC-signed per endpoint so the receiver can verify authenticity independent of transport.

What I'd change

The failure I keep thinking about is scope: there is still no multi-tenant auth — endpoint secrets authenticate receivers, not producers. Anyone with network access can register endpoints. That is documented, not hidden, and per-tenant API keys are the next change. After that: Alembic (currently create_all), Postgres + concurrent load numbers, and a Grafana dashboard on /metrics and queue depth. A portfolio project earns trust by stating its threat model plainly.
