HookFlow: accept first, deliver later

Webhook delivery is a persistence problem, not a POST problem.

The naive webhook sender does requests.post(customer_url, json=event) inside the request handler. That couples your API latency to the customer's worst day: their deploy, their timeout, their 500. I built HookFlow around the opposite order — persist the event and its delivery row first, acknowledge the producer, and let a worker own the unreliable part.

The ingest path validates (http(s) URL, JSON-serializable payload under 256KB), checks idempotency, then commits Event + Delivery(status=queued) in one transaction before touching Redis. Redis only carries a wake-up hint; the worker polls due rows regardless, so a dropped message delays delivery instead of losing it. Measured on SQLite via TestClient: 39 rps at p95 29ms for 1KB payloads — the cost is the transaction, not the bytes.

Two decisions were load-bearing. First, at-least-once plus idempotency keys instead of exactly-once claims: a UNIQUE(endpoint_id, idempotency_key) constraint plus an IntegrityError catch closes the race where two concurrent ingests both pass the app-level existence check — the loser returns the winner as deduplicated. Second, backoff with a dead end: 1m → 5m → 30m → 2h → 12h, then a dead-letter state with a replay endpoint that resets attempts (successes are not requeueable — replaying one would duplicate a side effect at the receiver).

The failure I keep thinking about is scope: there is still no multi-tenant auth — endpoint secrets authenticate receivers, not producers. Anyone with network access can register endpoints. That is documented, not hidden, and per-tenant API keys are the next change. A portfolio project earns trust by stating its threat model plainly.

HookFlow is available on GitHub.
