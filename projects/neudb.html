neuDB

Lightweight embedded Python database/storage engine exploring persistence, indexing, search, concurrency, and recovery.

Python (stdlib core) · PyPI 0.4.1 · 32 tests, CI — source · PyPI

Problem

Local prototypes and LLM agents need inspectable persistence without running PostgreSQL — and debugging what an agent "remembered" should be as simple as reading a file. I built neuDB to learn where stdlib persistence breaks, with the breakage documented rather than hidden.

Constraints

  • Zero dependencies for the core. Human-readable files (cat *.json is the debugger).
  • Honest scope: no server, no index, no transactions, no multi-process safety. Not a PostgreSQL competitor.

Architecture

Python library / CLI
  ↓
Table = one JSON file {id: record}
  ↓ (temp + fsync + os.replace)
Database = directory of tables
  ↓
Optional FastAPI / agent / dashboard (examples, not core)

Implementation

Each table is one JSON file mapping IDs to records. Writes go through temp-file + fsync + atomic os.replace, so a crash leaves the table fully old or fully new — never half-written. Same-process threads are serialized by a per-path threading.RLock held across reload-mutate-save. Search is brute-force: case-insensitive text plus cosine-similarity vector search with text fallback. Corrupt files raise a path-carrying CorruptedTableError instead of a bare traceback; stray temp files from interrupted writes are removed by an explicit maintenance call.

Engineering decisions

  • JSON files for readability and trivial backup/restore.
  • Atomic replace for crash-safe single-file writes.
  • Thread locks only — multi-process safety explicitly out of scope.
  • Brute-force scans to stay dependency-free; extras (api, agent) kept out of the core.

Challenges

While adding concurrency tests I first implemented temp-file sweeping on open — and the new test caught it deleting a live writer's temp file mid-write (FileNotFoundError in os.replace). Sweeping is now explicit maintenance with an age threshold, and the incident is documented in docs/recovery.md. The test suite earning its keep is the point of the project.

Benchmarks

Measured 2026-09-14 via benchmarks/bench.py (Python 3.11, local disk):

Workload2,000 rows (338KB)5,000 rows (847KB)
Insert138/s · p50 7.3ms · p95 13.7ms56/s · p50 17.5ms · p95 34.4ms
Full read2.6ms6.9ms
Text search2.9ms6.8ms
Threaded 4×100400/400 rows, 0 lost

Per-insert cost grows with file size — O(N) writes confirmed by measurement. Guideline: do not use past ~10K rows per table.

Trade-offs

  • Full-file rewrite per write and full-file load per read: simple and atomic, but linear cost.
  • No index, pagination, checksums, or backup rotation — documented in Limitations, not roadmap-vapor.
  • Embeddings bloat the JSON; vector search is linear scan over rows × dimensions.

Lessons

~900 lines of stdlib suffice for the experiment — and the measurement matters more than the code. The benchmark table is the real deliverable: it tells you exactly where this design stops being viable, which is what makes the next design (indexes, WAL, pages) concrete instead of theoretical.
