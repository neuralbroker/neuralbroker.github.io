Bugbee

AI developer infrastructure for coding, tool execution, persistent project context, and verification.

TypeScript · Bun · SQLite · Effect — original layer: Superharness (~350 lines) — source

Attribution first: Bugbee's shells (TUI, desktop, providers) are carried over from anomalyco/opencode under MIT (see NOTICE). My original work is the Superharness runtime layer: packages/bugbee/src/harness/, documented in docs/ARCHITECTURE.md and docs/CONFIG.md.

Problem

Coding agents lose project context, tool history, permissions, and verification state across real-repo work. Demos look autonomous; day-two usage is amnesia plus overconfident edits.

Constraints

  • Verification must never break the agent loop — a broken harness must fail open.
  • Every context injection must be bounded (output sizes, file counts, trace on disk only).
  • State must survive across runs as plain files, not hidden databases.

Architecture

User
 ↓
Agent (build: full tools · plan: docs-only · review: read-only, ≤80 steps)
 ↓
Tools (edit/write/bash/read/glob/grep/web, output-bounded, allow/ask/deny)
 ↓ plugin hook: tool.execute.after
Execution (admit → drain → provider turn, process-local)
 ↓
Verification (opt-in verify-after-mutate + doctor)
 ↓
Persistent Context (memory files + trace.jsonl + compaction epochs)

Implementation

An internal plugin hooks two points. After each tool call it appends a JSONL trace line (fire-and-forget, errors swallowed), then — only for mutating tools, only when the project opts in with commands configured — runs verify commands sequentially (200KB capture cap, SIGTERM→SIGKILL escalation) and injects the [harness.verify] report into the tool output with per-command exit codes, telling the model to fix failures before claiming completion. Memory is ≤20 Markdown files (8KB each) loaded as instructions; per-turn system hooks only point at the directory. Config merges top-level harness over legacy experimental.harness with safe defaults: verify off, memory on, trace off, 80-step ceiling.

Engineering decisions

  • Opt-in verification over blocking gates. Fast by default, verifiable when the project configures green, fast commands.
  • Permission-scoped modes over one omnipotent agent (build/plan/review).
  • File-based memory + trace over hidden state — inspectable with cat.
  • Fail-open hooks — config failures fall back to defaults; trace failures are swallowed.

Challenges

The tension is cost vs. safety: running tests after every mutation is correct and slow. The resolution is project-level opt-in with a timeout and output cap, so the harness degrades to "fast agent" instead of "stuck agent" on bad configuration. No success-rate or latency numbers are published — agent benchmarks require eval fixtures that don't exist yet, and inventing them would be fabrication.

Benchmarks

Harness unit behavior verified (config defaults, memory load, trace append, verify execution — 4 standalone checks passing). Upstream's 600+ tests are carried over untouched. No agent success metrics are cited, by policy.

Trade-offs

  • Process-local state: no clustering, trace file is the cross-run memory.
  • Single squashed upstream import — no upstream sync story yet.
  • Not a sandbox, scheduler, or eval framework; tool permissions come from upstream.

Lessons

Reliability for agents is systems engineering, not model quality: permissions, bounded context, durable state, and verification loops. The model is commodity; the harness is the product — and the harness must be boring enough to trust.
